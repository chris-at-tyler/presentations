to-spec · 2/3

What a spec carries

spec.md — the template, annotated
## Problem Statement      ← from the user's perspective
## Solution               ← the shape, before any detail
## User Stories           ← "a LONG, numbered list… extremely
                            extensive" — each independently checkable
## Implementation Decisions  ← what the grilling settled,
                            so it is never relitigated
## Testing Decisions      ← the seams, and what "done" means
## Out of Scope           ← the fence around the work

No file paths, no code snippets — they go stale fast. One exception: a prototype snippet that encodes a decision more precisely than prose (a schema, a state machine) gets inlined, trimmed to the decision-rich parts.

The user-story list is the load-bearing section — to-tickets slices against it next. "Extremely extensive" is a completion-criterion demand driving legwork (part 2 vocabulary, working).
to-spec · 3/3

Seams: where the tests will bite

Before writing anything, to-spec sketches the seams the feature will be tested at — and checks them with you.

  • 1Prefer existing seams to new onesevery new seam is surface area to maintain
  • 2Use the highest seam possibletest external behaviour, not implementation details
  • 3The ideal number is onea lot of functionality behind a small, stable interface — a deep module

Why this matters for agentic development: a durable interface gives tests something stable to target — the code underneath can be rewritten by an agent without the tests moving.

Deep modules = Ousterhout. The agent twist is real: agents churn implementation fast, so tests pinned to internals become the bottleneck. High-seam tests survive the churn.

to-tickets · 2/5

What makes a slice right-sized

  • Complete — a narrow but full path through every layer. Vertical, never horizontal.
  • Demoable on its own — a finished slice is verifiable end-to-end, which is what makes it safe to hand to an agent.
  • Sized to one fresh context window — the 2026 constraint: a ticket an agent can hold in its head, start to finish, without summarization losses. Work one ticket per fresh context; clear between tickets.
  • Prefactoring ordered first — "make the change easy, then make the easy change." If the code fights the feature, the first tickets reshape the code.
"Fits in a context window" as a sizing unit is genuinely new engineering vocabulary — flag it. Prefactoring is Kent Beck; it becomes ticket 00 when needed.
to-tickets · 3/5

Blocking edges & the frontier

01 join waitlistblocked by: none — frontier 02 nightly expiryblocked by: none — frontier
↓
03 cancellation → notifyblocked by: 01
↓
04 claim from emailblocked by: 03 05 hold expiry → nextblocked by: 03

Every ticket declares what gates it. The frontier = every ticket whose blockers are done. That's the parallelism story: several agents, each grabbing a frontier ticket, no coordination meeting required.

The DAG is the artifact. On a real tracker the edges are native blocking links; agents (or teammates) pull from the frontier. 01 and 02 can start simultaneously today; 04 and 05 run in parallel once 03 lands.
to-tickets · 4/5

The exception: wide refactors

One shape breaks the tracer-bullet rule: a mechanical change whose blast radius fans across the codebase — rename a column, retype a shared symbol. No vertical slice can land green. Sequence it as expand–contract:

1 · Expandadd the new form beside the old — nothing breaks → 2 · Migratemove call sites in batches sized by blast radius — CI stays green → 3 · Contractdelete the old form once no caller remains

Each migrate batch is its own ticket blocked by the expand; the contract is blocked by every batch. If even batches can't stay green alone, they share an integration branch and green is promised only at a final integrate-and-verify ticket.

Classic database-migration wisdom generalized to code. The skill encodes when to break its own primary rule — that's mature skill design (a branch, in part-2 vocabulary).
to-tickets · 5/5

The quiz gate: you approve before anything publishes

to-tickets, before publishing Here's the proposed breakdown (numbered, with blocking edges)…

· Does the granularity feel right — too coarse, too fine?
· Are the blocking edges correct — does each ticket only depend on what genuinely gates it?
· Should any tickets be merged or split?

Iterate until you approve; only then does anything hit the tracker — blockers first, so every edge references a real ticket, each labeled ready-for-agent.

Part 1's rule, resurfacing: facts are the agent's job; decisions are yours. Slicing granularity is a decision.

Also note what it does NOT do: never closes or modifies the parent issue. Local-files mode writes .scratch/<feature>/issues/NN-slug.md instead — same artifact, different medium; the demo uses that mode.

What A Run Produces · 1/3
demo/spec.md — excerpt
## Problem Statement
Campers find fully-booked sites and leave; cancelled
reservations sit unfilled. Both sides lose.

## User Stories (1–18 of 23)
1. As a camper, I want to join a waitlist for a sold-out
   site and date range, so that I get a chance at a spot.
2. As a camper, I want to be notified when I'm first in
   line for a freed spot, so that I can claim it.
3. As a camper, I want my claim link to expire visibly,
   so that I know when I've lost my window. …

## Implementation Decisions
- Strict FIFO queue per (site, date-range); offers are
  exclusive: one outstanding offer at a time. ← the grilling,
  carried faithfully — nothing relitigated
- Claiming converts the freed spot into an unpaid
  reservation; payment at check-in per park policy.
Fallback if live stalls, recap otherwise. Point at the traceability: every implementation decision maps to a DECISIONS.md line — the pipeline never re-opened a settled question.
What A Run Produces · 2/3

The proposed breakdown (the quiz gate)

  • 01Join a waitlist, end to end — button on sold-out page → entry stored → visible in account. Blocked by: none — can start immediately
  • 02Nightly season-close expiry — entries past season close expire. Blocked by: none — can start immediately
  • 03Cancellation → offer to first in line — freed spot creates an exclusive 4-hour offer + email. Blocked by: 01
  • 04Claim from the email link — valid claim converts offer to unpaid reservation. Blocked by: 03
  • 05Hold expiry → next in line — unclaimed offer lapses, next camper notified. Blocked by: 03
  • 06Entry caps — max 3 active entries per account, enforced at join. Blocked by: 01

Granularity right? Edges right? Merge or split? — you approve before anything publishes.

Each is a tracer bullet — 03 is demoable alone: cancel a booking in staging, watch the email arrive. Note 04+05+06 all unlock in parallel once their blockers land: that's the frontier widening.
What A Run Produces · 3/3
demo/.scratch/campsite-waitlist/issues/04-claim-from-email.md
# 04 — Claim from the email link

**What to build:** a camper who receives an offer email can
follow its link and claim the freed spot; the claim converts
the offer into a normal unpaid reservation (payment at
check-in). An expired link shows a clear "window closed"
state instead.

**Blocked by:** 03 — Cancellation → offer to first in line

**Status:** ready-for-agent

- [ ] Valid claim within the hold window creates the reservation
- [ ] The claim is exclusive — a second claim attempt fails safely
- [ ] Expired link renders the window-closed state
- [ ] No payment is requested at any point in the flow

End-to-end behaviour, not a layer list. Checkable acceptance criteria. A declared edge. An agent can grab this cold.

This single file is the talk's whole argument in miniature: part 1's decisions (payment at check-in), part 2's craft (checkable criteria, no vague bounds), part 3's pipeline (the blocking edge, ready-for-agent).
Wrap Up

Takeaways

  • Alignment and synthesis are different jobs. Grill to align; to-spec writes it down without re-asking. If the spec step interviews you, you grilled too little.
  • Slice vertically, size by context window. Every ticket a tracer bullet — demoable alone, small enough for one fresh agent context.
  • The edges are the parallelism. Tickets that declare their blockers form a frontier — that's how several agents work one feature without stepping on each other. npx skills@latest add mattpocock/skills → /to-spec · /to-tickets
