The New Rules of Context Engineering

Anthropic deleted 80%+ of Claude Code's system prompt for Claude 5 models — and nothing broke.
What that means for every CLAUDE.md, skill, and prompt we maintain.

Based on "The New Rules of Context Engineering for Claude 5 Generation Models" — claude.com blog, 2026
Sequel to part 2 ("write great skills") — same artifacts, new rules · ~5–10 min

Short one — news-style talk, not a workshop. Through-line: most of what we learned about prompting was written for models that needed babysitting. The Claude 5 generation doesn't — and Anthropic just proved it on their own product, at scale. Everything we maintain (CLAUDE.md files, skills, prompts) was written under the old assumptions.
The Experiment

They deleted 80% of the system prompt

Removed over 80% of Claude Code's system prompt for advanced Claude 5 models — with no measurable performance loss. — the blog's opening result, on their own flagship product
  • The old prompt was over-constraining. Rules written to protect weaker models now just force extra deliberation — the model burns effort reconciling instructions instead of working.
  • Real conflicts had shipped. One layer said "leave documentation as appropriate," another said "DO NOT add comments." Every response paid the tax.
  • Context has more places to live now. Memory, skills, deferred-loading tools — the system prompt no longer has to carry everything.
Emphasize this wasn't a lab benchmark — it's Claude Code, their most-used agent product. The conflict example is verbatim from the post; ask the room how many of our own instruction files might contradict each other, since nobody has ever audited them as a set.
The Map

Five shifts, one direction

  • 1Rules → Judgmentintent statements over never/always — the model can read the room now
  • 2Examples → Interface designexpressive parameters and enums instead of worked examples
  • 3Upfront → Progressive disclosureload context at the moment it's needed, not all at turn one
  • 4Repetition → Say it oncetool guidance lives in the tool description — nowhere else
  • 5Manual memory → Auto-memoryClaude saves relevant context itself; the # hotkey era is over

Bonus shift: markdown specs → rich references — HTML mockups, test suites, rubrics beat prose descriptions.

The one direction: away from controlling the model with prose, toward trusting its judgment and designing its environment. We spotlight shifts 1–3 next; 4 and 5 are self-explanatory (say things once; memory is automatic now — we already live with auto-memory daily).
Shift 1 · Rules → Judgment

From "never do X" to "match the room"

Claude Code system prompt — comment philosophy, then vs. now
THEN:
"Default to writing no comments.
 Never write multi-paragraph docstrings."

NOW:
"Write code that reads like the surrounding code:
 match its comment density, naming, and idiom."

The new line is shorter, covers more cases, and is right more often — judgment generalizes; rules don't. A "never" written for a heavily-commented codebase is wrong in a sparse one, and vice versa.

Keep hard rules where a miss is expensive — deploys, git pushes, production data. What got deleted was style micromanagement.

This is the emotional core of the talk. Every never/always we've written was a bet that we could enumerate the situations better than the model could judge them — that bet has flipped. But be precise: guardrails with real blast radius stay. The test: "if the model gets this wrong once, what does it cost?"
Shift 2 · Examples → Interfaces

The schema is the instruction

Todo tool — the enum does the teaching
status: pending | in_progress | completed

description:
"Keep exactly one item in_progress
 at a time."
  • ✓Zero worked examplesthe enum + one constraint yield correct behavior
  • ✓Zero tokens per turnexamples in a system prompt are paid for on every request
  • ✓Part 2 echosame lesson as leading words in skills — the artifact's shape steers behavior

If you're pasting usage examples to fix a misbehaving tool, the fix is usually a better parameter name, an enum, or a constraint in the description.

Frame for anyone building agents or MCP tools: interface design IS prompt engineering now. A well-named enum is worth a paragraph of examples, and it can't drift out of sync with the code the way examples do.
Shift 3 · Progressive Disclosure

Context on demand, not all at once

turn 1lean prompt: purpose + gotchas → task appearsskill loads its body → tool neededdeferred schema fetched → detail arrives exactly when relevant
  • The win is mechanical. Tokens not spent every turn, attention not diluted across 40 scenarios that don't apply to this task.
  • You already know this pattern. A skill is progressive disclosure: name + description always loaded, full body only when invoked. Long skills should split into files the same way.
Part 2 callback lands here: the room has written skills, so they've already done progressive disclosure without the vocabulary. The new part is that it's now the organizing principle for ALL context — system prompts and CLAUDE.md included, not just skills.
The Cheat Sheet

Where each kind of context belongs

System prompt

Product context and agent purpose — what world is this agent operating in? Where the real design effort goes when you build a custom agent.

CLAUDE.md

Lightweight. Repo purpose in a line, then gotchas and non-obvious patterns only. Never state what the model can see for itself.

Skills

Team opinions and best practices, loaded selectively. Split long ones into progressive-disclosure files. Don't over-constrain.

References

Code beats prose: HTML mockups, test suites, rubrics — @mentioned when needed. Higher fidelity in, better results out.

This is the slide to screenshot. The references quadrant deserves a beat: "make it look like this mockup" or "make this test suite pass" outperforms three paragraphs of description — the reference is unambiguous where prose never is.
Monday Morning

Auditing our own context estate

  • Hunt conflicts first. Instructions accrete in layers — global config, repo files, skills — and nobody has ever read ours as a single document. Contradictions cost every single turn. The blog's tip: claude doctor can audit an existing setup.
  • Rewrite never/always into intent. Keep the hard rules with real blast radius; convert style micromanagement into one "match the surrounding code"-shaped line.
  • Upgrade one workflow to rich references. Next UI task: hand the agent the mockup. Next bugfix: hand it the failing test. Compare against your prose-spec baseline.
Deliberately small asks — this is pruning on touch, not a rewrite sprint. The conflict hunt is the highest-value one: contradictions are pure waste, no judgment call required to delete them. Challenge: next time you touch a context file, delete more lines than you add.
Wrap Up

Takeaways

"Trust the model" replaces "control the model." — the blog's closing move, and the whole talk in five words
  • Context written for a weaker model is wrong for this one. Guardrails age — prune them on every touch, or they quietly become the bottleneck.
  • Design environments, not lectures. Interfaces, enums, progressive disclosure — structure beats prose, and it's cheaper per turn.
  • Your CLAUDE.md should be getting shorter. If it only ever grows, it's accumulating obviousness and conflict, not knowledge.
