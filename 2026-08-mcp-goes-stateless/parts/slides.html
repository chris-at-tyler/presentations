MCP Goes Stateless

The 2026-07-28 spec revision is the biggest architectural change since MCP launched —
and it just made building a server a weekend project instead of an infrastructure one.

Based on "Bringing MCP 2026-07-28 to Claude" — claude.com blog, July 28, 2026
Full spec: modelcontextprotocol.io/specification/2026-07-28 · ~5–10 min

News-style talk. Two audiences in the room: everyone consumes MCP daily (Jira, CI/CD, browser automation — all MCP servers in our sessions), and a few might build one. The stateless change matters to both. Fifth spec revision — MCP is iterating fast but this one is architectural, not incremental.

The Big Change

From session to request/response

Before

Bidirectional, stateful.

Long-lived sessions, server-side state to babysit, sticky processes to host — awkward on serverless, awkward behind load balancers.

Now

Request/response core.

A server is a plain HTTP workload. Serverless and edge friendly, scales like any web service, nothing to pin.

The stateless core makes MCP "a first-class HTTP workload with no session management to work around." — Netlify, from the announcement
Netlify's line is the whole story in one sentence — everything else in the release hangs off this change. If anyone asks where stateful interaction patterns went: they move into the extensions framework (next slide), out of the core.
Extensions

Apps & Tasks are official

MCP Apps

Interactive UI, inline in the conversation.

A server can render real interface — not walls of text — and users see what a connector did without switching context.

MCP Tasks

Long-running work, first-class.

Jobs that outlive a request/response cycle — syncs, builds, migrations — no longer need to be faked over polling hacks.

Both graduated from experimental status into versioned, formal extensions — and the framework is the real news: capabilities can now evolve without touching the core protocol.

Analogy that lands: extensions are to MCP what official middleware is to HTTP — the core stays small and stable, the interesting stuff versions independently. That's how a protocol survives its own growth.
Security

Enterprise auth, no more workarounds

  • 1OAuth 2.0 / OIDC compatibilityproduction-grade identity standards, not bespoke token schemes
  • 2Direct enterprise IdP integrationEntra and Okta named explicitly — the systems enterprises actually run
  • 3Enterprise-managed auth on Claude's sidean admin authorizes once per org; users inherit access through existing IdP groups — zero-touch on first login

What this retires: the API-key-per-developer pattern — every dev minting a personal token and stashing it in an env var or config file just to wire up a connector.

Most enterprise-relevant slide. Today's reality for most teams: personal access tokens sprinkled across dev machines — an offboarding and audit nightmare. IdP-group-governed access is how every other enterprise system already works; MCP just joined them. Adoption needs the server side to support it too — watch your vendors.

Tunnels gets the amber highlight deliberately — it's the one that changes what's reachable. Anything living on a private network could become a Claude-accessible server without an exposed endpoint. Research preview = right capability, wrong maturity; watch it, don't build on it.
What It Means · Consuming

Nothing breaks, three things to watch

  • Existing connectors keep working. Spec support is "rolling out across Claude products soon" — this is a migration target for servers, not a breaking change for users.
  • Watch vendor adoption for the auth win. When the servers we rely on adopt the new spec, per-dev API keys can give way to org-level, IdP-governed access. That's a request to make of vendors, not something we can flip ourselves.
  • Tunnels put private services in reach. Internal APIs and in-network tools become candidates for agent access without security exceptions — flag it for a future spike.
Deliberately calm slide — no action required today. The auth point is the one worth a follow-up: inventory which of our connectors still ride on personal tokens, so we know who to nudge and what to migrate when support lands.
What It Means · Building

A server is now a weekend, not a project

Stateless core

It's just an HTTP handler.

Deployable on whatever you already run — no session infrastructure, no sticky routing, no special hosting.

Tasks

Long jobs fit natively.

Data syncs, migrations, report generation — the protocol now models work that takes minutes, not milliseconds.

Apps

Results as UI.

A lookup tool can return an interactive view instead of a text wall.

Ideas, not commitments — a read-only internal lookup server is the classic first candidate: low risk, immediately useful in every agent session.

The barrier-drop is the takeaway: pre-revision, "should we build an MCP server" meant session infrastructure questions. Now it's a plain HTTP endpoint speaking a well-documented protocol. If someone in the room has an internal system agents keep needing data from — that's the candidate.
Wrap Up

Takeaways

  • Stateless is the story. Serverless hosting, simpler servers, standard scaling — every other headline in the release follows from the core going request/response.
  • Extensions are the future-proofing. Apps and Tasks graduate, and the framework means capabilities version without spec churn.
  • Auth is the enterprise unblock. OAuth/OIDC plus IdP-group inheritance ends the personal-token workaround era — as soon as your vendors adopt it.
