The Thesis
"A skill exists to wrangle determinism out of a stochastic system." — writing-great-skills

Predictability is the root virtue: the agent takes the same process every run — not the same output.

A brainstorming skill should predictably diverge: its tokens vary, its behaviour doesn't. Cost and maintainability are symptoms of predictability, not rivals to it.

This reframes everything: you're not writing documentation, you're engineering behaviour. Every lever in the next 20 minutes is judged against one question — does it make the process more repeatable?
The Central Trade

Every skill spends one of two loads

Model-invoked

Keeps a description → the agent can fire it on its own.

The description sits in the context window every turn — that's context load. Other skills can reach it too. You can still type its name.

User-invoked

disable-model-invocation: true → only you can fire it.

Zero context load — but now you are the index that must remember it exists. That's cognitive load, the price of human agency.

Split, inline, disclose, invoke — most authoring decisions are this same trade made in different places.

Part 1 callback: grill-me had disable-model-invocation: true and never appeared in the model's own skill list. Now they know why — it costs nothing in the window; the presenter pays with one memory slot instead. Cognitive load isn't bad — spend it where human judgement matters.
The Central Trade

When cognitive load piles up: a router

ask-mattuser-invoked router — names every skill and when to reach for it
↓   points the human at   ↓
grill-me to-spec triage tdd wayfinder …

User-invoked skills have no description, so nothing can fire them but you — a router can only hint. One skill to remember instead of twelve: cognitive load collapsed back to a single slot.

This is real: Matt Pocock's repo ships ask-matt as exactly this router. The elegance — the cure for too many user-invoked skills is one more user-invoked skill.
The Toolkit · 1/5

Writing the description

The description is the skill's trigger and its permanent rent — every word is context load on every turn. So it earns the hardest pruning:

❌ six triggers, one branch
Use when the user wants to write a
commit message, needs to commit
changes, asks for help committing,
wants to make a commit, mentions
git commits, or is committing code.
✅ one trigger per branch
Write commit messages — use when
committing changes.
  • 1Front-load the leading wordthe description is where it does its invocation work
  • 2One trigger per branchsynonyms renaming the same branch are duplication
  • 3Cut identity that's in the bodytriggers only, plus any "when another skill needs…" clause
The left example is from our demo patient — they'll see it again. Six phrasings of "user is committing" is one branch written six times.
The Toolkit · 2/5

The information hierarchy

A skill's content, ranked by how immediately the agent needs it:

  • In-skill steps — the ordered actions, the primary tier. What the agent does. Each ends on a completion criterion.
  • In-skill reference — rules and facts consulted on demand. Sometimes the whole skill — a flat set of review rules is fine, not a smell.
  • Disclosed reference — pushed to a linked file behind a context pointer, loaded only when needed. writing-great-skills does exactly this: SKILL.md keeps the levers, GLOSSARY.md holds the full definitions.

Progressive disclosure is the move down the ladder. Push too little and the top bloats; push too much and you hide what every run needs. That tension is the whole decision — and it's not about tokens, it's about keeping the top legible.

Branching is the disclosure test: inline what every path needs, disclose what only some paths reach. And co-location: once material lands on a rung, keep a concept's definition, rules, caveats under ONE heading — scattered fragments don't get read together.
The Toolkit · 3/5

Completion criteria

The condition that tells the agent a unit of work is done. Two properties make it a lever:

❌ vague — invites quitting early
Review the message until it
looks good.

Clarity: can the agent tell done from not-done? A fuzzy bound gives way to the pull of the next step — premature completion.

✅ checkable + exhaustive
Done when every functional change
in the diff is named in the message
— no hunk unaccounted for.

Demand: how much it requires sets the legwork — the digging the agent does within the step.

"Every modified model accounted for" forces thorough work where "produce a change list" doesn't. Defence order for premature completion: sharpen the bound FIRST (cheap, local); only hide later steps if the criterion is irreducibly fuzzy and you actually observe the rush.
The Toolkit · 4/5

Leading words

A compact concept already in the model's pretraining that the agent thinks with while running the skill — a behavioural principle in one token, recruiting priors you don't have to pay for.

"fast, deterministic, low-overhead" → tight

One quality restated three ways collapses into a single pretrained word: a tight loop.

"a loop you believe in" → red

A fuzzy gate becomes a binary observable: the test goes red on the bug, or it doesn't.

Remember grill-me's description? "A relentless interview…" — that word is doing engineering. "Be thorough" changes nothing (the agent is already thorough-ish); relentless beats the default.

You win twice: fewer tokens, and a sharper hook for the agent's thinking. Assume every skill carries restatements a leading word can retire.

Deepest idea in the talk. Coined words work but recruit no priors — you pay in definition tokens what a pretrained word gives free. In the description it anchors invocation; in the body, execution. Same word in your prompts/docs/code = the agent links the language to the skill.
The Toolkit · 5/5

Pruning: the no-op test

  • 1Single source of trutheach meaning in exactly one place — changing behaviour is a one-place edit
  • 2Relevancedoes this line still bear on what the skill does, or has the world moved on?
  • 3The no-op test, sentence by sentencedoes it change behaviour versus the model's default? If not — delete the sentence, don't trim it
No-op specimens "Always be helpful, clear, and accurate."  ·  "Use good judgment."  ·  "Write high-quality code."

The model already does all of that by default — you're paying load to say nothing. Be aggressive: most prose that fails the test should go, not be rewritten. Verdicts are settled by running the skill, not by debate.

This is the discipline slide. Adding feels safe, removing feels risky — that asymmetry is exactly how skills rot. Note the no-op test is model-relative: two people disagreeing are disagreeing about the default.
Failure Modes · 1/2

The length diseases

Sediment

Stale layers that settle and never clear.

Adding feels safe, removing feels risky — the default fate of any skill without a pruning discipline. "TODO: update after the migration (2024)."

Duplication

One meaning, multiple sources of truth.

Costs maintenance and tokens — and inflates the meaning's prominence past its real rank on the ladder.

Sprawl

Simply too long — even if every line is live.

Attention thins across the excess. Cure: the ladder — disclose reference, split by branch or sequence.

Three distinct diagnoses that all present as "this skill is long": stale length (sediment), repeated length (duplication), and length itself (sprawl). Different cures — that's why the vocabulary matters.
Failure Modes · 2/2

The behaviour diseases

Premature completion

Declaring done before the work is.

Attention slips to being done. Visible later steps pull forward; a vague criterion gives way. Sharpen the bound first.

No-op

A line the model obeys by default.

Perfectly relevant, changes nothing. "Be thorough" → already thorough-ish; pay for relentless or pay for nothing.

Negation 🐘

"Don't think of an elephant."

A prohibition names the behaviour into the frame — "never write verbose comments" makes verbosity the freshest pattern in context. Prompt the positive: "write one-line comments."

Negation is the crowd-pleaser — everyone has written "don't do X" into a prompt and watched X happen. The forbidden concept activates strongly; the "not" is a weak modifier. A prohibition earns its place only as a hard guardrail you can't phrase positively, and even then pair it with the positive target.

The After

34 lines → 9. Same behaviour, every run.

demo/flawed-skill/SKILL.refactored.md
---
name: commit-helper
description: Write commit messages — use when committing changes.
---

1. Run `git diff --staged` and read every hunk.
2. Write the message: imperative subject ≤ 50 characters; body
   explains why, wrapped at 72.
3. Done when every functional change in the diff is named in
   the message — no hunk unaccounted for.

One trigger. One source of truth for the 50-char rule. Negations flipped positive. A checkable, exhaustive completion criterion. Nothing the model does by default.

The wrap line: same agent, same model — only the writing changed. That's predictability as an engineering property. Steps are now the top of the ladder; there's nothing left to disclose because there's nothing left.
Wrap Up

Takeaways

  • Predictability is the root virtue. Same process every run, not same output — judge every line of a skill against that. "A skill exists to wrangle determinism out of a stochastic system."
  • Every decision spends one of two loads. Context load (the agent's window) or cognitive load (your head) — split, inline, disclose, and invoke accordingly. Router skills collapse cognitive load back to one slot.
  • Edit like an engineer. One source of truth · the sentence-level no-op test · positive phrasing · leading words that beat the default. npx skills@latest add mattpocock/skills → /writing-great-skills

And everything here applies beyond skills — your CLAUDE.md and your prompts are skills too.
